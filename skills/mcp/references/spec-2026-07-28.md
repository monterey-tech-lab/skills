## Stateless core

- No protocol-level sessions; **`Mcp-Session-Id` removed** from Streamable HTTP for the 2026-07-28 core.
- No required **`initialize` handshake**; each request carries protocol version and client capabilities (typically `_meta` keys `io.modelcontextprotocol/protocolVersion`, `io.modelcontextprotocol/clientCapabilities`).
- Cross-call application state uses **explicit server-minted handles** passed as tool arguments—not sticky Redis protocol sessions.
- List endpoints must not depend on per-connection session state.

**Incorrect:** teach Redis + `Mcp-Session-Id` affinity as the modern production default.  
**Correct:** request-scoped Streamable HTTP; keep Durable Objects/Redis only for real app state if needed.

## Discovery and results

| RPC / field | Requirement |
|---|---|
| `server/discover` | Servers **MUST** implement; advertises supported versions, capabilities, identity |
| `resultType` | Results use `"complete"` or `"input_required"` (MRTR replaces many server-initiated requests) |
| Caching on list/read | Include `ttlMs` and `cacheScope` (`public` \| `private`) — see [Caching semantics](#caching-semantics) |
| Streamable HTTP POST headers | Include `Mcp-Method`, `Mcp-Name` (SEP-2243) |

Removed versus older revisions: `ping`, `logging/setLevel`, `notifications/roots/list_changed` (among others in the changelog). Tasks live under extension `io.modelcontextprotocol/tasks`.

## Caching semantics

List/discover/read complete results should carry:

| Field | Meaning |
|---|---|
| `ttlMs` | How long a client/gateway may reuse the payload |
| `cacheScope: "public"` | Same for all callers—**catalogs that are not user-specific** |
| `cacheScope: "private"` | Per-auth / per-user—**default for anything that depends on identity or ACL** |

**Incorrect:** `cacheScope: "public"` on a user’s private issue list or tenant-scoped resources (shared caches can leak across auth contexts).  
**Correct:** `private` for user/tenant data; `public` only for truly shared catalogs (e.g. public docs index). Invalidate on `list_changed` when the set changes.

Edge/CDN: cache only `public` list/discover metadata—never private tool-call bodies.

## Gateway headers

Streamable HTTP POST should include routing headers so proxies can classify traffic without parsing the JSON body:

**Incorrect:** bare POST JSON with no `Mcp-Method` / `Mcp-Name` (gateways cannot route/auth by method).  
**Correct:** set `Mcp-Method` and `Mcp-Name` per SEP-2243; optional custom headers via documented `x-mcp-header` patterns when required.

## Tool annotations

Set risk vocabulary on tools:

- `readOnlyHint` / `destructiveHint` — **required default** for new tools; Claude connectors expect them
- Also consider `idempotentHint` / `openWorldHint` when accurate

Annotations are **hints for hosts**, not a security boundary. Enforcement and HITL → `ai-security`.

## Transports

| Transport | Role under 2026-07-28 |
|---|---|
| **Streamable HTTP** | Default for **new remote** servers |
| **stdio** | Default for **local** IDE subprocess servers; never log JSON-RPC to stdout |
| **HTTP+SSE** | **Deprecated**; host compatibility only |

Prefer [Google Cloud MCP overview](https://docs.cloud.google.com/mcp/overview) (2026-07-28-aligned) over older consumer explainers that still say “stdio + SSE only.”

## Deprecated features

Entering the Active → Deprecated → Removed lifecycle (≥12 months): Roots, Sampling, Logging; HTTP+SSE; OAuth **DCR** for new implementations; some `includeContext` values. Prefer CIMD and current capability models for new work—except hosts that **reject DCR** (use their static-client recipe).

## Dual-era hosts

Much production software still speaks **2025-11-25**. New servers should emit 2026-07-28 fields (`resultType`, `ttlMs`, `cacheScope`) and may need dual-compat while hosts catch up. Claude Code versions that predate those fields can fail tool fetch—upgrade the host or keep intentional dual-compat.

## Progressive discovery

Hosts may list servers broadly but inject tool definitions only after search/inspect ([client best practices](https://modelcontextprotocol.io/docs/2026-07-28/develop/clients/client-best-practices)). Server authors: precise descriptions, annotations, deterministic `tools/list` order. Deep host sandbox / “code mode” implementations are out of scope for this skill—point host builders at client best practices.

## Agent Skills intersection

| Concept | Meaning |
|---|---|
| Agent Skills as **authoring aids** | Skills such as MCP.org / Anthropic `build-mcp-server` that guide server design (discover before code; deployment paths) |
| MCP **Skills extension** | `io.modelcontextprotocol/skills` — server publishes skills via `skills/list` / `skills/get` and resources (often `skill://…`) |

Advertise the extension in `server/discover` when publishing skills. Do not claim that “using a skill to write an MCP server” is the same feature as “MCP server hosts skills.”

## Auth notes

- Prefer CIMD over Dynamic Client Registration for **new** OAuth clients when the host supports it.
- Some first-party remotes **reject DCR** (e.g. Slack, GitHub)—use static client ID / documented `auth` blocks instead.
- Validate issuer (`iss`) per hardened OAuth guidance in the changelog.
- Capability setup uses env interpolation and host OAuth; allow-list / no token passthrough → `ai-security`.
